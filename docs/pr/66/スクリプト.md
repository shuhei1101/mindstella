## 変更方針

| 対象 | 方針 | 補足 |
| --- | --- | --- |
| 版のファイル | ワークスペースの直下の `mindstella-version.ini` の 1 行目に `v{メジャー}.{マイナー}.{パッチ}` を書く。無ければ版を記録する前の形式として扱う。ER 図『ワークスペース』に足す | - |
| プラグインの版 | スクリプトが自分の版を読めるよう、`plugins/mindstella/version.ini` に持つ。この PR で `v0.3.0` にする | - |
| `init` | 作るときにプラグインの版を版のファイルに書く | 開発中もプラグインの版は形と揃っている（要件.md の `### 版の記録`） |
| 手順の置き場所と形 | `plugins/mindstella/skills/mindmap/migrations/{版}/steps.yaml` と `scripts/`。`steps.yaml` は決まった操作（`rename_file`・`move_dir`・`delete`・`rename_key`・`set_default`・`map_values`・`call`）の並びで、JSON Schema で点検する | Schema の置き場所と各操作の引数はインターフェース定義設計で決める |
| 最初の版の手順 | 今の `migrator.py` の中身（資料の `done` → `status`、設定の `summary`）を、版を記録する前の形式から `v0.3.0` への手順（`migrations/v0.3.0/`）に移す | `summary` は値が要るため、点検で利用者に聞く側へ回す |
| `migrate` | `--from`・`--to` の間の版の手順を版の順に当てる。版のファイルは書き換えない（要件.md の `### 移し替えのスキル` の 7 のとおり、点検と値の入力の後に書き換える）。ワークスペース全体のスキーマとの突き合わせはせず、手順そのものが失敗したときだけエラーで終わる（突き合わせは後の `check` が担う）。`--plan` は当てずに手順を版の順に返し、破壊的な操作に印を付ける。値が要るキーは `--set` で入れ、`--record` が点検に合うときだけ版のファイルを書く | インターフェース定義『記録の形式の移行』。今の `--summary` は `--set mindmap.yaml:summary=...` に置き換える |
| 写しと戻し | `migrate` が当てる前に写しを取り（git の作業ツリーの中ならワークスペースのパスだけをコミット、そうでなければ隣のフォルダへ複製）、途中で失敗したら写しから戻して、失敗した版・手順・理由を返して終わる | - |
| 版の比較 | `migrate --plan` で `--from`・`--to` を省くと、ワークスペースの版とプラグインの版を比べた `relation` と当てる手順を返す。スキルはこれ 1 回で版を比べる | - |
| 前の版の形式の案内 | `check` の問題の詳細と、書き込むコマンドのヒントの向け先を、移し替えのスキルに直す | - |
| 開発側の点検 | 最新のタグ（`v*` のタグを版の順に並べた先頭）の `schemas/` と今の `schemas/` を比べ、違うのに `migrations/` に「最新のタグより新しく、プラグインの版以下」の版が無ければ落ちるテストを置く | タグが無い clone では skip するかをテスト作成で決める |
