# 要件

## 要望

記録の検索と書き込みを project-index に任せ、commit・スレッド・ID の採番など MindStella に固有の機能を MindStella の MCP に残す（資料 A-107 の No 2。構成は資料 A-119・A-106、ツールの行き先は A-107 の「MindStella の MCP のツールの行き先」に従う）。
project-index には MindStella のための変更を入れない。

<!-- table: data -->

| 要件 | 終わりの条件 |
| --- | --- |
| ワークスペースの配信 | ワークスペースの作成で、記録を project-index の配信元として配信する設定（配信元の行の `config`）を記録のフォルダに配置する。project-index の `search_docs` で、検討事項・資料などの項目が 1 件ずつの文書としてヒットし、`write_docs`・`delete_docs` で書き込める。配信元の行が配信される状態になる |
| 資料の本文の検索 | 資料などの本文（`.mindstella/docs/{ID}.md`）が、`search_docs` の本文の条件でヒットする。管理用の YAML（`files.yaml`）の行に記載する場合、行の入れ方は #344 の本文の D-173〜D-177 に従う |
| 資料の本文の書き込みと部分更新 | 資料などの本文（`.mindstella/docs/{ID}.md`）を、項目の追加・更新と同じく書き込め、本文の一部だけを指定して書き換えられ（#515 の置き換え）、その変更が履歴に残る。書き込みは project-index の `write_docs` で行う（下の確認ログの決着） |
| 関連のたどり | 項目の参照を `related` の `{to, type}`（種類 `depends_on`・`parent`・`for`・`see_also`）で持ち、project-index の `trace_related` で参照元・参照先を種類つきでたどれ、`delete_docs` が参照されている項目の削除を断る。既存のワークスペースは移し替えで書き換える。画面の関連の表示・入力も種類つきの `related` を読み書きする |
| 記録の検索と書き込みのツール | MindStella の MCP から `find`・`show`・`add`・`update`・`remove`・`batch`・`tags`・`attrs`・`impact` を削除し、project-index の `search_docs`・`write_docs`・`delete_docs`・`trace_related` で同じことができる |
| `edit_option`・`adopt`・`check` | MindStella の MCP に残す（単一ユースケース設計で決めた）。`edit_option`・`adopt` は同じ記号の案・採用している案・最後の案の検査と、採用する案の切り替えと状態の決定済みを 1 回で当てることが汎用の `write_docs` で表せないため、自分で履歴を記録して書き込む。`check` は MindStella に固有の決まり（参照切れ・本文のずれ・案と状態・重なった ID・スレッド）を洗い出し、スキーマ違反は project-index の書き込みの検査が止める |
| ID の採番 | MindStella の MCP に `next_id` を追加し、項目を追加する前に種類ごとの次の ID を取得できる。並行して取得した ID が重ならない。重なった ID を変更の検知が見つけたら、画面と MindStella のセッションに通知する |
| 変更の検知 | MindStella の MCP と画面の書き込みは、誰が書き込んだかを付けて自分で履歴に記録する。それ以外の変更はワークスペースのフォルダの監視で見つけ、項目の履歴と通し番号に記録する。MindStella のセッションの応答の途中（UserPromptSubmit から Stop まで）の変更はそのセッションの変更とし、それ以外は外部の変更として、MindStella のセッションのまとまりに混ぜず別のまとまりに自動で commit する。Git の操作（checkout・merge）による書き換えは記録しない |
| commit とスレッド | `commit`・`pending`・スレッドのツールを MindStella の MCP に残す。スレッドの書き込み（`new_thread`・`reply`・`set_thread_status`・`update_thread`）と `commit` は、MindStella のセッションの `session_id` の呼び出しだけを受け付ける |
| `changes_since_read` | 外部の変更を含めて、前回参照した時点より後の変更を返却する |
| 画面 | 画面の書き込みは今と同じく履歴に残る。変更履歴で外部の変更のまとまりを見分けられ、重なった ID の通知が表示される |
| 既存のワークスペースの移し替え | 今のバージョンのワークスペースを移し替えると、配信の設定が配置され、新規作成したワークスペースと同じく project-index で検索・書き込みできる |
| MCP の案内 | MindStella の MCP の instructions が、記録の検索と書き込みは project-index で行うことを案内する |

配信の設定のファイル名は `.mindstella/dev-docs.yaml` にする（インターフェース定義設計のレビューで決定）。#516 で登録した配信元の行の `config` をそのまま使える。

資料の本文の書き込みの手段（確認ログの決着）: project-index に、`body_file` が指す本文のファイルを `write_docs` の `set`・`text_edits` で書き込む汎用の変更を起票した（[project-index#83](https://github.com/shuhei1101/project-index/issues/83)）。
この PR は project-index#83 に依存し、project-index#83 のリリースの後にマージする。project-index#83 の契約で、`write_docs` の本文のキーと、`body_file` の列（このワークスペースでは `body`）の名前がぶつからない書き方が決まったら、スキルの手順（session の `SKILL.md`・`steps/取り込み.md`）とインターフェース定義『話し合いの進行』の本文の書き方を、その契約のキーで確定させる（実装の工程で行う）。資料の本文は、project-index#83 で入る `write_docs` の本文の書き込みで書く（レビューの指摘で、モックのまま 0.13.0 に入ると本文を書き込む手段が無くなるため、本物への付け替えを別の Issue に分けず、この PR で行う）。

project-index（develop の `4a9d816`）の `write_docs` は、`records` の要素（YAML の 1 項目）だけを書き換え、`body_file` が指す本文のファイルは書き込まない（`src/project_index/features/write/service.py` に `body_file` の扱いが無く、`delete_docs` も要素を除くだけで本文のファイルを残す。`tests/unit/project_index/features/write/test_service.py` の `test_delete_docs_when_records`）。
このリポジトリの `dev-docs.yaml` の `records: files`・`body_file: path` の文書 1 件（`plugins/mindstella/skills/mindmap/playbooks/壁打ち.md`）へ、`text_edits`（`field: body`）を `dry_run: true` で指定した `write_docs` は、時間切れで結果が返らなかった（[project-index#81](https://github.com/shuhei1101/project-index/issues/81)）。
同じ呼び出しを測り直すと、`文字列ではない項目は置き換えられません` の違反で断られた（2026-11-15）。

関連のたどりの手段（確認ログの決着）: この PR で、参照のキー（検討事項の `depends_on`・`parent`、タスクの `for`・`depends_on`、項目の `related`）を `related` の `{to, type}` に移し、専用のキーをやめる（D-275 B を前倒しする）。#390 の `{to, type}` の設計と移し替えの方針を使う。

project-index（develop の `4a9d816`）が関連として読むのは、文書のメタデータの `related` に並ぶ `{to, type, source}` の行だけで（`src/project_index/features/related/graph.py` の `related_links`）、MindStella の記録は参照を ID の文字列の配列で持っていたため、そのままでは `trace_related` も `delete_docs` の参照の検査もたどれなかった。

## #345 から引き継いだ材料の扱い

| 材料 | 扱い | 理由 |
| --- | --- | --- |
| #390 の関連を `{to, type, when}` にする設計の `type` | 受け継ぐ。参照のキーを `related` の `{to, type}` に移す設計の材料にする（確認ログの決着） | project-index の `related` の型にそのまま当たる |
| #390 の `when` | 捨てる（スコープ外の行で、レビューで確定する） | project-index の `related` は `when` を持たず（project-index のインターフェース定義『関連のたどり』）、project-index には MindStella のための変更を入れない |
| #390 の既存のワークスペースの移し替えの方針 | 移し替えの設計の材料にする | 参照のキーのスキーマを変えるときに、同じく既存の記録を移し替える |
| #390 の関連の表示・入力のモック | モック作成の材料にする | 参照のキーを `related` の `{to, type}` に移すと、画面の関連の表示・入力も種類つきの関連を読み書きする |
| `batch` の `op: show` を残す | 残さない。`batch` ごと削除する | A-107 で `batch` の行き先は `write_docs`。`write_docs` は 1 回の呼び出しで複数の操作をまとめて当て、追加する項目の ID は `next_id` で先に取得するので、`$番号` で先に追加した項目を指す必要が無い。書き込んだ後の中身は `search_docs` で参照する |
