### 変更方針

<!-- table: {"kind": "data"} -->

| 対象 | 方針 | 補足 |
| --- | --- | --- |
| データ | プリセットは `config.yaml` の `presets` に、名前・説明・タグの式・並び順を持つ。タグの式は knowledge の規約『フィルター・照合条件の構造』の `and`・`or`・`not` の束と、`field: tags` の条件で持ち、入れ子は 3 レイヤーまで | ER 図『ワークスペース』で決定 |
| 式の評価 | タグの値は `tag_text.py` の正規化（NFKC と小文字）で比べ、プリセットごとに該当する項目の件数を数える | ツール・点検・記録の取得が同じ数え方を使用する |
| 作成・更新・削除 | MCP で作成・更新・削除し、結果にそのプリセットに該当する件数を返却する。名前の重複・空の束・4 レイヤー以上の入れ子はエラーにする | ツールのインターフェースは `未確定`（決める工程: インターフェース定義設計） |
| 配信 | 記録の取得と配る書き出しにプリセットと該当する件数を掲載する | 画面に並べるのは #361 |
| 点検 | 該当する件数が 0 のプリセットを `check` の警告にする | - |
| エージェントフロー | エージェントフロー『記録』の「話題のタグを付ける」「既存の記録にもタグを付ける」の後に、プリセットを作る・見直す工程を追加し、AI が利用者に頼まれなくてもプリセットを作る。実行条件は、新しいタグを付けたときと、タグを付けた項目が増えたとき | 公開ドキュメントの更新は [要件.yaml](./要件.yaml) の更新ドキュメント |
| プリセットを作る目安（ガイド） | 工程の本文に、作るとき（同じタグか、よく一緒に付くタグの組を持つ項目が一定数あり、それに該当するプリセットが無い）・直すとき（作ったプリセットの式のタグが改名・統合された、該当する件数が 0 件になった）・作らないとき（1 件にしか付かないタグ、既存のプリセットと該当する項目が同じ）と、名前・説明・並び順の付け方を記載する | 件数の目安の値はエージェントフローの設計で決める |

### 変更方針

<!-- table: {"kind": "data"} -->

| 対象 | 方針 | 補足 |
| --- | --- | --- |
| 本文の参照 | `docs/` のフォルダの `resolve()` をワークスペースごとに 1 回にし、本文 1 件ごとのパスの解決とファイルの存在の確認を減らす | 本文のパスがワークスペースの外を指さないことの検査は残す |
| 応答の保持 | ワークスペースごとに組み立てた応答の本文と `ETag` を保持し、記録が変わっていない要求には保持した応答を返却する | 作り直す契機は `未確定`（決める工程: インターフェース定義設計） |
| 圧縮 | 要求が `Accept-Encoding: gzip` を持つとき、保持した応答を gzip で圧縮して返却する。圧縮した本文も保持する | - |
| 再検証 | 応答に `ETag` を付け、`If-None-Match` が一致する要求には本文の無い 304 を返却する。`Cache-Control` は `no-cache` にして毎回再検証させる | 画面はブラウザの再検証で 304 をそのまま扱え、画面の変更は要らない |
| 性能 | `/mnt/c` のワークスペース（本文 805 件）で、記録が変わっていない 2 回目以降の記録の取得を 0.1 秒未満にする | 1 回目の時間は本文の参照の改善の分だけ減る |
| 既存機能への影響 | 応答の本文の構造は変えない。配る書き出しは記録を埋め込むため、保持と圧縮の対象にしない | - |
