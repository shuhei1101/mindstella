<details markdown="1">
<summary>計測の内訳</summary>

- `run_update` のプロファイルでは、`yaml.safe_load`（純 Python の解析）が 9 回で処理時間の約 7 割を占める
- ファイルの読み取りそのものは、`/mnt/c` でも 1 ファイル 0.01 秒以下で、解析が支配的
- 同じ YAML を C 実装の `CSafeLoader` で読み込むと、`docs.yaml`（1.6MB）は 0.68 秒から 0.09 秒、`decisions.yaml`（1.2MB）は 0.85 秒から 0.16 秒、`threads.yaml`（1.6MB）は 0.79 秒から 0.10 秒になる
- `yaml.safe_dump` は 1 ファイル 0.4〜0.5 秒かかる

</details>

## 変更方針

<!-- table: data -->

| 対象 | 方針 | 補足 |
| --- | --- | --- |
| YAML の読み込み・書き出し | `store.py` の `load_yaml_text`・`dump_yaml` を libyaml の C 実装（`CSafeLoader`・`CSafeDumper`）にし、`threads.py`・`history.py` の読み込みも `load_yaml_text` を使用する | libyaml を持たない PyYAML では今の Python の実装で読み書きする。読み込んだ値は変わらず、書き出しは長い文字列の折り返しの位置だけが変わる |
| 検証の範囲 | 書き込む関数は、差し替えていないファイルの検証に、同じ中身（バイト列の要約が同じ）の前回の検証の結果を使用する | 差し替えていないファイルの問題で書き込みを止める今の振る舞い（前の版の形式の案内を含む）は変えない |
| スレッドの読み取り | `run_thread` はワークスペース全体を読み込まず、`threads.yaml` と、向けた項目の種類の YAML だけを読み込む | - |
| 速さの決定値 | 非機能要件『記録の更新とスレッドの操作の時間』を 1 秒以下で追加する | - |
| 速さのテスト | 結合テストで、実例と同じ件数の記録を持つワークスペースを作り、4 つの操作が上限の時間に収まることを確認する | - |

### 計測

Issue の実例のコピーで、1 回の操作が読み込み・検証・書き出ししたファイルと時間（Linux の領域。3 回測った幅は `## 現状` の表）。
`/mnt/c` に置いた場合との差は、どの操作も 0.1 秒以内だった。

| 操作 | 合計 | 主な内訳 |
| --- | --- | --- |
| `update` | 3.0 秒 | 7 種類と設定の読み込み 1.9 秒・全体の検証 0.4 秒・`docs.yaml` と `changes.yaml` の書き出し 0.6 秒 |
| `thread` | 4.9 秒 | 7 種類と設定の読み込み 2.0 秒（タイトルを引くだけ）・`threads.yaml` の読み込み 2 回 2.2 秒・書き出し 0.6 秒 |
| `update_thread`（取り込み済み） | 1.6 秒 | `threads.yaml` の読み込み 1.0 秒・書き出し 0.5 秒 |
| `set_thread_status` | 1.5 秒 | `threads.yaml` の読み込み 0.9 秒・書き出し 0.6 秒 |

C 実装に替えただけの試算は `update` 0.98 秒・`thread` 1.07 秒・`update_thread` 0.44 秒・`set_thread_status` 0.39 秒で、`update` に残る全体の検証 0.37 秒と `thread` に残る全体の読み込みを、検証の結果の記録とスレッドの読み取りの範囲の変更で省く。
