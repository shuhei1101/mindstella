# ワークスペースを今のバージョンへ移し替える

プラグインを上げた後に、ワークスペースのバージョンの移し替えを確かめたいときに実行する。

## 前提

- [プラグインをインストールする](./セットアップ手順-プラグインをインストールする.md)
- 移し替えるワークスペース（`.mindstella/config.yaml` か、直下の `config.yaml`・`mindmap.yaml` があるフォルダ）

## 手順

### 起動スクリプトで立ち上げる

ワークスペースのフォルダを渡して、起動スクリプトを叩く（[起動スクリプトで立ち上げる](./セットアップ手順-起動スクリプトで立ち上げる.md)）。

```bash
{プラグインのフォルダ}/bin/mindstella {ワークスペースのフォルダ}
```

常駐サーバーがワークスペースを開く前に、ワークスペースのバージョンとプラグインのバージョンを比べる。
同じで、そのバージョンの手順を全て当て終えていれば（バージョンのファイルの 2 行目の数が手順の数以上なら）、何も書き換えずに開く。
同じバージョンに後から追加された手順があれば（2 行目の数より後ろの手順か、2 行目が無い v0.14.0 以上のバージョンではそのバージョンの手順の全て）、その手順を当てる。v0.14.0 の手順は 2 度当てても結果が変わらない。v0.14.0 より前のバージョンで 2 行目が無いときは、そのバージョンの手順を当て終えたものとして扱う。
ワークスペースのバージョンが古ければ、利用者に確かめずに、ワークスペースのバージョンの残りの手順からバージョンの順に当てて今のバージョンへ移し替える。

### 移し替えの中身

常駐サーバーがコピーを取ってから、手順を当てる。
コピーは、ワークスペースが git の管理下ならコミット、そうでなければ隣のフォルダ `{フォルダ名}.before-{バージョン}` への複製になる。
途中で失敗すると、コピーから自動で元に戻り、起動スクリプトが失敗したバージョン・手順・理由を出して止まる。
ワークスペースのバージョンの方が新しいときは、何も書き換えずに、プラグインの更新を案内して止まる。

v0.5.0 の手順で、設定の `field` が、同じ名前 1 件のプレイブックの配列 `playbooks` へ移る（例: `field: システム開発` → `playbooks: [システム開発]`）。
最上位の軸の呼び名（`target_label`）は書き換わらない。

v0.6.0 の手順で、設定ファイル `mindmap.yaml` が `config.yaml` に改まり、直下の記録のファイルとフォルダが全てサブフォルダ `.mindstella/` に移る。
中身は変わらず、直下には `.mindstella/` だけが残る。
前のバージョンの画面 `preview.html` と、直下の `.mindstella.lock` は消える。
今ある項目には編集した人（`updated_by`）を追加せず、次に書き換えるまで、編集した人が分からないものとして扱う。

v0.7.0 の手順で、`決定済み` で回答（`answer`）を持ち案を持たない検討事項に、回答を内容・理由を理由にした採用した案が 1 つ作られる。
ほかの検討事項は、この手順では変わらない。

v0.8.0 の手順で、送信（`submissions.yaml`）の 1 件ごとに、スレッドが `threads.yaml` に追加され、`submissions.yaml` は消える。
取り込み済みの送信は、書き込みが取り込み済みのクローズのスレッドになり、次の取り込みで記録し修正されない。
取り込んでいない送信は、オープンで取り込んでいない書き込みを持つスレッドになり、次の MindStella のセッションが拾う。
送信の向けた項目・箇所・本文・送信した日時は、スレッドの最初の書き込みに引き継がれる。

v0.10.0 の手順で、項目とスレッドが使っているタグが、説明なしで設定の `tags`（語彙）に登録される。
項目とスレッドのタグは変わらない。

v0.11.0 の手順で、設定の `tags`（タグの説明を含む語彙）が削除される。
項目とスレッドのタグは変わらない。

v0.12.0 の手順で、項目のタグが、名前と主題のマーカーを持てる形状（`{name: 通知}`）に置き換わる。
並びと表記は変わらず、移し替えた直後はどのタグも主題を持たない。
表記をそろえて同じ名前になるタグは、最初の 1 件だけが残る。
スレッドのタグと、項目の更新日時・変更履歴は変わらない。

v0.13.0 の手順で、資料の Markdown の、今の書き方の引数のマーカーが JSON の記載（`<!-- table: {"kind": "data"} -->`）に、flow・sequence の図が map の図に書き換わる。
図で使っていた種類は、設定の `mdmark.map` に入る。
map に写せない値（図の `scope`・`updated` ほか）は、資料と行つきで示される。
書き換えには mdmark の CLI を `npx` で取得して使うため、Node.js とネットへの接続が要る。

v0.14.0 の手順で、設定の `goal`・`phases`・`playbooks`・`targets`・`target_label`・`categories` が削除される。
項目の対象（`target`）・カテゴリー（`category`）は `topic:{値}` のタグになり、属性（`attrs`）は本文の末尾の「属性」の表に、調査の観点（`angles`）と確かさ（`confidence`）は本文の末尾の「観点と確かさ」の表に移る。
項目のフェーズ（`phase`）・資料の納品物のマーカー（`deliverable`）・検討事項の影響度（`weight`）は削除される。
Markdown の本文 `.mindstella/docs/{ID}.md` は `{ID}.mark.md` へ改名され、項目の `body` と変更履歴の改名前の `body` も改名後のパスに書き換わる。HTML の本文は変わらない。
続けて、本文の `.mindstella/docs/` と埋め込むファイルの `.mindstella/files/` がワークスペースの直下の `docs/`・`files/` へ移り、項目の `body` と変更履歴の `body` が `../docs/{ID}.mark.md` の形式に書き換わる。項目の変更履歴の回は増えない。
`.mindstella/release/` は削除される。ワークスペースを Git で管理していれば、移し替えの前の commit から戻せる。
ワークスペースの直下に、記録とは関係の無い `docs/` か `files/` が既にあると、移し替えは失敗して元の中身に戻り、ワークスペースは開かない。そのフォルダを改名してから再度開く。
最後に、削除したネットワークの見た目の既定（設定の `display.network_look`）が削除される。`display` がほかの値を持たなければ `display` も削除される。

### 移し替えの報告を受け取る

手順の後に値が要るキー（設定の `summary` など）には、仮の値（`summary` はフォルダの名前）が入る。
移せなかった値と仮に入れた値は、MindStella のセッションの起動の注入で知らされる（[続きを再開する](./話し合い-続きを再開する.md#状況を受け取る)）。
仮の値は、MindStella のセッションに伝えるか、プレビューの設定の画面で書き換える。

## 反映

即時。

## 確認

#### バージョンが書き換わっている

```bash
head -n 2 {ワークスペースのフォルダ}/.mindstella/mindstella-version.ini
```

1 行目にプラグインのバージョン（例: `v0.3.0`）、2 行目にそのバージョンの手順の数が出る。

#### 問題が無い

Claude Code に、mindstella の `check` ツールを、`workspace` にワークスペースのフォルダを渡して呼ぶよう頼む。

結果の `ok` が `true` になる。

## 元に戻す

移し替えた後に戻すときは、示されたコピーから戻す。

#### コピーが git のコミットのとき

```bash
git -C {ワークスペースのフォルダ} restore --source {コピーのコミットの ID} --staged --worktree -- .
git -C {ワークスペースのフォルダ} clean -fd -- .
```

ワークスペースのパスがコピーのコミットの中身に戻り、コミットに無いファイルが消える。

#### コピーがフォルダの複製のとき

ワークスペースのフォルダの中身を削除してから、複製したフォルダの中身を書き戻す。

戻した後も、コピーは残る。
要らなくなったら削除する。
