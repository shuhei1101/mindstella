# 要件

## 要望

話し合いの進行（`session`）の手順を、次のとおりに直す。

| 決まり | 内容 | 元 |
| --- | --- | --- |
| 検討事項の案 | 検討事項を足す段階で、AI が案（`options` の `key`・`content`・`pros`・`cons`）を書いて足す。決まったこととして足すときは、選ばれた案を `adopted: true` にする。ヒアリングは検討事項が持つ案を案の表に出し、案の無い検討事項は案を書き足してから聞く | D-21 |
| タスクを積む | AI がやる作業も利用者に頼む作業も、話し合いの中で出た時点でタスクとして積む | D-41（担当の部分は #26） |
| 納品物の資料 | ゴールの納品物が決まった段階で資料（`deliverable: true`・`status: 下書き`）を作り、本文に概要・背景・最終的な構成（見出しの並び。Issue などテンプレートのあるものはその見出し）を先に置いて、ゴールの納品物の `doc` から指す。セットアップで決めたゴールの納品物は、話し合いの最初の取り込みで資料を作る。以降は決まったことに合わせて本文を書き足す | D-28 |
| 記録は確かめずに書く | 記録（検討事項・タスク・調査・資料・用語集・メモ・会話ログ）は、状況が変わるたびに利用者に確かめずに足し、書き換える。利用者に確かめるのは、GitHub への起票などワークスペースの外へ書き込むときだけ。設定（`mindmap.yaml`）の書き換えは記録に含めない。決まりは `session` の SKILL.md の `## 記録の書き方` に置く | D-49 |
| 用語集に足す | 一般的でない言葉（システムの名前・業務や製品の固有の言葉・話し合いで決めた呼び名）は、利用者が指定しなくても用語集に足す。既存のプロジェクトのコード・ドキュメントを読んだときも、固有の言葉を足す。一般的な技術の言葉は、利用者が指定したときだけ足す | D-51 |
| タスクの成果と資料 | タスクで作った成果は 1 件ずつ資料にし、タスクの `related` から指す。成果の資料は、ゴールの納品物に当たるときだけ `deliverable: true` にする。タスクを完了にする前とゴール判定のときに、成果と資料が 1 対 1 で揃っているかを確かめ、欠けていれば資料を足す | D-52 |

## スコープ外

| 項目 | 理由 | 対応予定 |
| --- | --- | --- |
| 話題ごとのタグを作って付ける決まり（D-29） | 受付でタグの入れ物を作る側へ渡した | [#47](https://github.com/shuhei1101/mindstella/issues/47) |
| タスクの担当（AI / 利用者）を持たせる（D-41 の担当の部分） | 受付で担当を足す側へ渡した | [#26](https://github.com/shuhei1101/mindstella/issues/26) |
| 検討事項の選択肢をスキーマと `add`・`update` の検査で必須にする・推奨の項目を足す | 手順ではなくスキーマとツールを変える要望 | [#86](https://github.com/shuhei1101/mindstella/issues/86) |
| 調査のタスクの成果を資料にする | 調査は一次情報をまとめたもので、成果はリサーチの手順で調査の記録に書いて検討事項に繋ぐ。資料は調査を踏まえて今の話し合いで使える形にしたもので、作るのは作業・検証のタスクの成果 | 予定なし |
| 範囲の見直しの確定・リサーチのサブエージェントの起動前の確認・ゴール判定の確定 | 記録の書き込みではないため「記録は確かめずに書く」の外で、今の確かめを残す（範囲の見直しのフェーズの付け替えは #44 の D-32） | 予定なし |
| ゴール判定のツール `goal` で、タスクの成果と資料の 1 対 1 を判定する | D-52 は AI が確かめる決まりで、ツールの判定は変えない | 予定なし |
