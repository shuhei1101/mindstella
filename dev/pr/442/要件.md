# 要件

## 要望

[dev-docs.yaml](https://github.com/shuhei1101/mindstella/blob/develop/dev-docs.yaml) に、まだ掲載していない Markdown とソースコードを管理用の YAML（`files.yaml`）で加え、dev-docs の `search_docs` でタグ・概要文・関連から検索できるようにする。
設計書の YAML と目次は [#395](https://github.com/shuhei1101/mindstella/pull/395)・[#397](https://github.com/shuhei1101/mindstella/pull/397) で掲載済みで、この PR は残りを扱う。

| 要件 | 終わりの条件 |
| --- | --- |
| Markdown とソースコードを `files.yaml` に記載する | 下の「掲載する範囲」のファイルが、除外の条件（生成物・ロック・バイナリ・ベンダーのコード・再エクスポートや空の `__init__` だけのファイル）に当たるものを除いて 1 行 1 ファイルで並び、`dev-docs.yaml` の `records: files`・`body_file: path` の行から読める |
| 行に `name`・`description`・`tags` を入れる | `description` は 1 文で「何を受け持つか」と「どんなときに読むか」。`tags` は `topic:`・`tool:` だけ（`kind`・`scope` は付けない）。付ける前に `search_docs` の `group_by: tags`（`source: *`）で使われているタグを調べ、同じ意味のタグを使い回す |
| コード側の行に `related` を入れる | `implements`（コード → 設計書。モジュール構成の要素の `container` と `directory`・部品設計の `implementation`・画面設計の `screen` が指すファイルは全て）・`tests`（テスト → コード）・`see_also` を、コード側の行にだけ記載する。`dev-docs.yaml` の `related.types` に `implements`・`tests` を入れる |
| 行を作る手段 | dev-docs の `/dev-docs:setup`（`python -m dev_docs files`）が出す行の候補から作り、手で行を並べない |
| 検索できることを確認する | dev-docs の `check_project` で違反が無く、`search_docs` で `tags`・`description` から Markdown とコードの文書が返り、`trace_related` で設計書から `implements` のコードが返る |

掲載する範囲（`python -m dev_docs files` が出した行の数）:

| 範囲 | 中身 | 行の数 |
| --- | --- | --- |
| `docs/` | 利用者向けのページ（はじめに・使い方・リファレンス） | 18 |
| `dev/設計書/` | `デザイン方針.md` | 1 |
| `plugins/mindstella/` | スキルの手順の Markdown（`SKILL.md`・`steps/`・`playbooks/`・`references/`）、サーバーとプレビューのコード、ワークスペースの JSON Schema、移し替えの手順、プラグインのマニフェスト | 174 |
| `frontend/` | React のプレビューのコードとテスト・`openapi.yaml` | 48 |
| `tests/` | 単体・結合・E2E のテストと fixture・補助 | 315 |

tsc が生成した `.js`・ビルドした SPA・`route-tree.gen.ts` は、生成物として行の `exclude` で除く。

`index.yaml` から生成する `README.md` は、目次の行（`kind: index`）で掲載済みのため除く。

`files.yaml` の置き方は、AI Monitor の [dev-docs.yaml](https://github.com/shuhei1101/ai-monitor/blob/develop/dev-docs.yaml)（フォルダごとの `files.yml` と、行ごとの `exclude`）に合わせ、ファイル名も `files.yml` にする。
行の `exclude` は管理用の YAML 自身にも当たるため、`files.yaml` の名前では `*.yaml` を除く行（`docs/`・`dev/設計書/`）が自身を読めなくなる。

設計書の YAML にタグを持たせるか: 案 A で確定（reviewer の判定。案 A はテンプレートを変えないため、ユーザーへ回さない）

設計書のスキーマ（`dev/テンプレート/*.schema.yaml`）は `tags` の列を持たず、今の 304 件はタグが 0 件。
列を追加すると規約『ユーザー確認が必須な事項』のテンプレートの改訂に当たる。
スキーマは AI Monitor の配布物が元で、AI Monitor の設計書のスキーマも `tags` を持たない。

| 案 | 内容 | メリット | デメリット |
| --- | --- | --- | --- |
| A | この PR ではスキーマを変えず、タグは `files.yaml` の行だけに付ける。設計書の YAML のタグは、AI Monitor の配布元でスキーマに `tags` を追加する Issue（[shuhei1101/ai-monitor#3082](https://github.com/shuhei1101/ai-monitor/issues/3082)）の追従で入れる | 配布物と食い違わない | 設計書はこの PR の時点ではタグで検索できない（名前・概要文・本文では検索できる） |
| B | この PR で mindstella のスキーマに `tags` を追加し、設計書の YAML 304 件にタグを付ける | この PR で設計書もタグで検索できる | AI Monitor の配布物へ追従するたびに食い違いを解く手間が出る |

推奨: A

テンプレートの元は AI Monitor で、全プロジェクトのスキーマへ同じ列を入れるほうが追従の食い違いが出ないため。

`dev/設計書/デザイン方針.md` を YAML に変えるか: 案 A で確定（reviewer の判定。案 A はテンプレートを作らないため、ユーザーへ回さない）

| 案 | 内容 | メリット | デメリット |
| --- | --- | --- | --- |
| A | Markdown のまま `files.yaml` に記載する | AI Monitor の手順（判定フローチャート『モック要否』・planner『デザインスタイル選定』）が `設計書/デザイン方針.md` のパスで読むのを壊さない | 本文とメタデータを別のファイルで持つ |
| B | 新しいスキーマを作って YAML に変える | 設計書と同じく本文をキーで持てる | テンプレートの新規作成が要り、AI Monitor の手順が読むパスと食い違う |

推奨: A

AI Monitor の手順が Markdown のパスで読むため、変えると手順側の修正が先に要る。
