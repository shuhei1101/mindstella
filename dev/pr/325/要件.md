# 要件

## 要望

利用者がプレビューの画面から項目と設定を直し・足し・消し、変えた分をまとめて保存できるようにする。
保存した変更は、AI が次の話し合いの最初に前回読んだ時点からの変更として受け取る。

<!-- table: data -->

| 項目 | 要件 |
| --- | --- |
| 編集できるもの | 設定（題名・プレイブック・フェーズ・ゴール・対象・カテゴリー・タグの語彙など `update_settings` が書き換えるキー）と、全ての種類の項目（検討事項・タスク・調査・資料・用語集・メモ・会話ログ）のキーと本文。検討事項の案の追加・書き換え・削除と、採用する案の切り替えを含む。ID・作成日時・更新日時・編集した人・変更履歴は編集できない |
| 取り下げと対象外 | 検討事項を `対象外`・`取り下げ` に、タスクを `中止` にでき、調査・資料・用語集・メモ・会話ログを取り下げにできる（今の状態と `withdrawn` のキーで表す） |
| 項目の追加 | 種類ごとの画面から項目を足せる。ID はサーバーが振る |
| 項目の削除 | 項目を消せる。ほかの項目が指している項目は消さず、指している項目を示す（MCP の `remove` と同じ扱い） |
| 編集の溜め方 | 編集・追加・削除はその場で確定せず、保存待ちとして溜める。溜めた編集は画面を開き直しても残る |
| 変えた箇所のバッジ | 保存待ちの編集がある項目と、その項目の中の変えたキー・案に、変えたことを示すバッジを付ける。一覧（マップ・ボード・カード・表）の項目にも付ける |
| 1 件ずつの取り消し | 保存待ちの編集を、1 件ずつ取り消せる。1 件は、項目のキー 1 つ・本文・案 1 つの追加と書き換えと削除・採用する案の切り替え・設定のキー 1 つと、項目 1 つの追加・削除 |
| まとめての保存 | 保存の操作で、保存待ちの編集を全て 1 回で確定する。1 件でも書き込めないものがあれば何も書かず、書き込めない編集と理由を示す |
| 編集した人 | 保存で書く項目の `updated_by` と変更履歴の `by` を `user` にする |
| 差分の表示中 | 差分を見るモードの間は編集の操作を出さない。編集するには差分の表示を外す |
| AI への受け渡し | 保存した変更は、AI が話し合いの最初に呼ぶ `changes_since_read` の `added`・`changed`・`removed` に、`by` が `user` の変更として載る。session の手順は、利用者が画面で変えた分を AI の変更と分けて示す |
| 書き込みの入口 | サーバーに、保存待ちの編集の読み・追加・書き換え・取り消しと、まとめての保存のエンドポイントを開ける |
| 配る書き出し | 配る書き出しの 1 枚の HTML は見るだけのまま、編集の操作を出さない |

<!-- /table -->

`未確定`: 保存待ちの編集の置き場所（決める段: インターフェース定義設計）

| 案 | 内容 | メリット | デメリット |
| --- | --- | --- | --- |
| A | ワークスペースの `.mindstella/` に溜める（レビュー中のコメントと同じ置き方） | 端末を変えても・ブラウザを閉じても残り、コメントと同じ溜めて送る作りに揃う | 記録の形（ER 図）に保存待ちの編集のファイルが増える |
| B | ブラウザの端末の保存領域に溜める | サーバーとワークスペースの記録の形が変わらない | ほかの端末から見えず、保存領域を消すと編集が消える |

推奨: A

レビュー中のコメントを `.mindstella/` に溜めて送る作りが既にあり、同じ操作の形に揃えると利用者が覚えることが増えない。

`未確定`: 編集を溜めた後に AI が同じ項目を書き換えたときの扱い（決める段: インターフェース定義設計）

| 案 | 内容 | メリット | デメリット |
| --- | --- | --- | --- |
| A | 編集を溜めた時点の項目の `updated` を控え、保存の時点で変わっていたらその項目の編集を書き込めない編集として示す | AI の書き換えを黙って上書きしない | 利用者が編集をやり直す手間が出る |
| B | 保存の時点の項目に、変えたキーだけを重ねて書く | 書き込めない編集が出ない | 同じキーを AI が書き換えていると、AI の値を黙って上書きする |

推奨: A

AI が話し合いで書いた値を、利用者が気づかないまま消すことを防ぐ。

`未確定`: 保存した変更を書き換えのまとまりにするか（決める段: インターフェース定義設計）

| 案 | 内容 | メリット | デメリット |
| --- | --- | --- | --- |
| A | 保存で、利用者の編集だけを 1 つのまとまりにする（説明は利用者が任意で書き、空なら既定の文） | 変更履歴の時点に利用者の保存が 1 つの単位で出る | AI のまだまとめていない変更があるとき、先にそれを分けるか混ぜるかの決まりが要る |
| B | まとまりにせず、AI が次の話し合いで説明を付けてまとめる | サーバーの作りが変わらない | session の手順が利用者の保存を「まとめ忘れ」としてまとめ、説明が利用者の意図と合わない |

推奨: A

変更履歴で選ぶ時点に利用者が保存した単位が出ると、差分を見るモードで利用者の変更だけを読み返せる。

## スコープ外

| 項目 | 理由 | 対応予定 |
| --- | --- | --- |
| 編集できる人を役割で絞る（オーナー・管理者） | メンバーと役割を足す [#25](https://github.com/shuhei1101/mindstella/issues/25) を取り下げており、ワークスペースに役割が無い | 予定なし |
| 資料のテンプレート（登録・資料との紐づけ・版の更新の取り込み） | テンプレートの Issue が扱う | [#16](https://github.com/shuhei1101/mindstella/issues/16) |
| 配る書き出しの 1 枚の HTML での編集 | サーバーが無く書き込む先が無い | 予定なし |
| 項目に確認済みの印を付ける | 別の Issue が扱う | [#188](https://github.com/shuhei1101/mindstella/issues/188) |
