# 要件

## 要望

親 [#365](https://github.com/shuhei1101/mindstella/issues/365) の決定（D-8・D-13・D-14・D-16・D-20〜D-23）に従い、React 移行の土台を配置してトップバーと概要の画面を移行する。
子 6（[#371](https://github.com/shuhei1101/mindstella/issues/371)）で切り替えるまで、今の画面（`/mindstella.html`）とその部品・ストーリー・テストはそのまま配信し、動かし続ける。

<!-- table: data -->

| 対象 | 要件 |
| --- | --- |
| ビルド | Vite（React + TS）でビルドし、tsc は型検査（`--noEmit`）だけに使う。React Compiler を入れ、新しいコードで `useMemo`・`useCallback` を記載しない |
| スタイル | Tailwind v4 を使い、トークンを `:root` の 3 ティアで持って `@theme inline` で割り当てる。`--color-*: initial` で色の標準のパレットを削除する |

| ルーター | TanStack Router にし、URL の状態は `validateSearch` + Zod で持つ |
| サーバーのデータ | TanStack Query にし、Provider と QueryClient は 1 つにする |
| 配信 | ビルドした SPA の `index.html` をサーバーが配信する。今の画面のパスは変えず、SPA は別のパスで配信する |
| Storybook | `@storybook/react-vite` の設定を、今の `.storybook/` とは別に配置する。データは MSW と props で差し込む |
| lint・検査 | eslint-plugin-better-tailwindcss（任意値の禁止）・eslint-plugin-boundaries（`app・routes → features → shared` の向き）・react-hooks・jsx-a11y・複雑さの lint を error で入れる。Storybook の addon-a11y と Playwright の axe で画面を検査する |
| Git フック | lefthook と、リポジトリの直下の `package.json` の npm scripts で、lint・型検査を commit の前に実行する |
| トップバー・概要 | 部品設計『トップバー』と画面設計『概要』の要素と操作を全て再現する。見た目は shadcn/ui・Tailwind に合わせて一新してよい |

`未確定`: 配信と API の定義の方式（決める段: インターフェース定義設計）

今のサーバーの配信（`scripts/serve.py`）は FastAPI・OpenAPI を持たず、親の決定 D-14（FastAPI が `index.html` と API を配信する）・D-22（orval で生成する）をそのまま当てられない。

| 案 | 内容 | メリット | デメリット |
| --- | --- | --- | --- |
| A | `serve.py` を維持し、配信の API の OpenAPI の定義をインターフェース定義から記載して、orval で TanStack Query の hook・Zod・MSW のモックを生成する | 利用者の端末の依存（PyYAML・jsonschema・mcp）が増えない | OpenAPI の定義と `serve.py` の実装が一致しているかを、テストで検査する必要がある |
| B | 配信を FastAPI へ移し、OpenAPI を自動生成して orval で生成する | OpenAPI と実装が常に一致する | 利用者の端末の依存に FastAPI が増え、依存の確認と動作環境の変更が要る |
| C | OpenAPI を作らず、query と MSW の handler を手で記載する | 定義と生成の工程が無い | D-22 から外れる。MSW の handler と API の一致をテストで検査できない |

推奨: A

依存の確認（`check_env.py`）と動作環境を変えずに、knowledge の規約の生成物（hook・Zod・MSW）を揃えられる。

`未確定`: フロントのソースの置き場所（決める段: モジュール構成設計）

knowledge の規約『ビルド構成』は Vite の `root` を `frontend/` にするが、利用者へ配るのは `plugins/mindstella/` の中身だけで、ビルドの出力をプラグインの中に配置する必要がある。

| 案 | 内容 | メリット | デメリット |
| --- | --- | --- | --- |
| A | ソースをリポジトリの直下の `frontend/` に置き、ビルドの出力を `plugins/mindstella/skills/mindmap/preview/` の下へ出して commit する | 規約どおり。ソースを利用者へ配らない | ソースと出力が別の場所になり、出力の commit 漏れを検査する必要がある |
| B | ソースもプラグインの中（`plugins/mindstella/skills/mindmap/preview/` の下）に置く | 今の配置と同じ | 規約から外れる。ソースと開発用の設定を利用者へ配る |

推奨: A

規約に従い、利用者へ配るものをビルドの出力だけにできる。

`未確定`: 単体テストのランナー（決める段: モジュール構成設計）

| 案 | 内容 | メリット | デメリット |
| --- | --- | --- | --- |
| A | React の部品と画面は Vitest + Testing Library で確認する | knowledge の規約『Unit / Component テスト』どおり。MSW の handler を共有できる | 今のフロントの単体テスト（pytest-playwright）と、子 6 まで 2 系統になる |
| B | 今と同じ pytest-playwright で確認する | テストの系統が 1 つで済む | 規約から外れる。React の部品を関数として呼べない |

推奨: A

子 6 で今の画面とテストを削除した後は Vitest の 1 系統になり、規約の handler の共有もできる。

`未確定`: TypeScript のバージョンと型情報つきの lint（決める段: PoC 検証）

今の TypeScript 7 は typescript-eslint が動かず（外部ライブラリ『typescript』の制限）、knowledge の規約『ESLint・Prettier・tsconfig』が求める `@typescript-eslint/no-deprecated`（`parserOptions.projectService`）を動かせない。

| 案 | 内容 | メリット | デメリット |
| --- | --- | --- | --- |
| A | React の側は typescript-eslint が対応するバージョンの TypeScript で型検査と lint を回す | 規約の型情報つきの規則を全て入れられる | 今の画面（TypeScript 7）と、子 6 まで 2 つのバージョンが並ぶ |
| B | TypeScript 7 のまま、型情報の要らない規則だけを入れる | バージョンが 1 つで済む | `no-deprecated` など、型情報つきの規則が入らない |

推奨: A

規約が error で求める規則を欠かさずに入れられる。PoC 検証で、React の側の型検査・lint・Vite のビルドが同じ構成で通ることを確認する。
