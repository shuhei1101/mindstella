# 要件

## 要望

資料（`docs.yaml` の項目）の本文を、Markdown に加えて HTML でも書けるようにする。

- 資料の本文は Markdown か HTML のどちらか 1 つで持ち、どちらで書いたかを記録から読める
- AI は項目の追加・更新で、資料の本文を HTML で渡せる。Markdown から HTML へ、HTML から Markdown へ書き換えたときは、前の形式の本文のファイルを残さない
- 項目の表示・記録の取得・配る書き出しは、HTML の本文も Markdown の本文と同じく返す・埋め込む
- ワークスペースの点検は、HTML の本文も「指す本文が無い」「どこからも指されない本文」の対象にする
- 本文のファイルの書き換えで画面が読み直すのと同じく、HTML の本文の書き換えでも読み直す
- 資料の一覧（カード・ボード・表）と詳細のヘッダーに、本文の形式のバッジを付ける（HTML の資料は `HTML`、Markdown の資料は `MD`）
- HTML の資料も、詳細のサイドバー・拡大表示（詳細の全画面）で、描いた結果を開ける
- HTML の資料でも、選んだ箇所へコメントを付けられる。付けたコメントは Markdown の本文と同じく、本文の行の範囲を箇所に持ち、点検・送信で今の本文と照らせる
- HTML の本文はプレビューの画面の見た目と処理を壊さない（本文の CSS が画面へ漏れない・本文のスクリプトが画面の記録や操作に触れない）
- 全体の検索は、HTML の本文と、Markdown の本文の中の言語指定 `html` のコードブロックを、タグではなく描いた文で当てる
- ゴール判定で納品物の HTML の資料を書き出すときは、HTML のまま `{納品物のタイトル}.html` に書く
- Markdown の本文の中の言語指定 `html` のコードブロックも、コードではなく描いた結果で出す。描き方は HTML の本文と同じ（本文の CSS が画面へ漏れない・スクリプトを動かさない）

`未確定`: 本文の形式の持ち方（決める段: インターフェース定義設計）

| 案 | 内容 | メリット | デメリット |
| --- | --- | --- | --- |
| A | 本文のファイル名の拡張子（`{ID}.md` / `{ID}.html`）で形式を表し、入力は `body_markdown` と並ぶ `body_html` で受ける（両方は渡せない） | 今の `body` のキーと Markdown の資料をそのまま使え、移し替えが要らない | 拡張子を見ないと形式が分からない |
| B | 資料に `body_format`（`markdown` / `html`）のキーを足し、本文は 1 つの入力キーで受ける | 形式を記録のキーで読める | 既存の資料にキーが無い状態を既定で扱う必要があり、入力キーの名前も変わる |

推奨: A

本文のファイルは既に `body` のキーが名前で指しており、拡張子で形式が決まれば記録のキーも既存の資料の移し替えも増えない。

HTML の本文は、`sandbox="allow-same-origin"`（`allow-scripts` なし）の iframe の `srcdoc` に描く（PoC で成立。プレビューの計画書の `## PoC 結果`）。
HTML の本文で選んだ箇所は、サーバーが Python の標準ライブラリ `html.parser.HTMLParser` で開きタグに足した原文の行の印（Markdown と同じ `data-line`）から本文の行の範囲にし、照らし合わせも同じパーサーでタグを外した描いた文で行う（同上）。

変更履歴・前回からの差分で、HTML の本文は、変えた後の描いた結果の上で変わった行を含む要素に印を付けて見せ、「原文の差分」に切り替えると原文の行の差分（足した行・消した行）を出す（モック作成でユーザーが選んだ。[確認ログ](./確認ログ.md)）。
