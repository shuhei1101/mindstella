# 要件

## 要望

stdio で動く MCP サーバーを、HTTP（Streamable HTTP）で待ち受ける常駐サーバーに移す。
1 つの常駐サーバーを並行する複数のセッションが共有し、複数のワークスペースを扱う。
合わせる規約は knowledge の『MCP サーバー作成ルール』（shuhei1101/knowledge#50 で HTTP に統一し、stdio を禁止した）。

<!-- table: data -->

| 要件 | 終わりの条件 |
| --- | --- |
| トランスポート | サーバーは stdio で動かず、`127.0.0.1` の `MINDSTELLA_PORT`（無ければ 8784）で Streamable HTTP の `/mcp` を待ち受ける。stdio の起動の経路は残さない |
| 接続の設定 | プラグインのルートの `.mcp.json` に `"type": "http"` と `"url": "http://127.0.0.1:${MINDSTELLA_PORT:-8784}/mcp"` で書く。Claude Code の中のツールの名前は `mcp__mindstella__{ツール}` から `mcp__plugin_mindstella_mindstella__{ツール}` に変わり、スキルの `allowed-tools` と呼び出しを合わせる。起動スクリプトが起動ごとに MCP の設定を書いて `--mcp-config` で渡す仕組みは削除する。起動スクリプトを通さずに立ち上げた Claude Code でも、常駐サーバーが待ち受けていれば mindstella のツールを使える |
| 常駐サーバーの起動と管理 | 常駐サーバーを起動・停止でき、待ち受けているポートを確認できる。Claude Code を立ち上げたときに常駐サーバーが落ちていれば起動する |
| 複数のワークスペース | 1 つの常駐サーバーが、ツールの引数 `workspace` で指したワークスペースを読み書きする。相対パスの基準のセッションの作業フォルダは、PreToolUse のフックがツールの引数に入れる（サーバーのプロセスの作業フォルダを使わない） |
| ペインへの入力の宛先 | コメントをまとめて送った後に貼る先（tmux のソケット・ペイン・`CLAUDE_CONFIG_DIR`・作業フォルダ）を、サーバーのプロセスの環境変数ではなく、そのワークスペースを指してツールを呼んだセッションから受ける。値は PreToolUse のフックがツールの引数に入れる。2 つのセッションが別々のワークスペースのプレビューを開いたとき、それぞれのプレビューから送ったコメントがそれぞれのセッションのペインに貼られる。値を入れたセッションが終わった後は貼らず、ログに残す |
| プレビューの配信の寿命 | プレビューの配信は常駐サーバーのプロセスに付き、セッションを閉じても止まらない。常駐サーバーを止めたときに全ての配信を止め、終了時のフックを配信ごとに呼ぶ |
| 外から見る設定 | `MINDSTELLA_ALLOWED_HOSTS`・`MINDSTELLA_PREVIEW_START_HOOK`・`MINDSTELLA_PREVIEW_STOP_HOOK` を、常駐サーバーを起動する環境から読む |
| 状態の持ち方 | ツールの処理はモジュール変数にセッションごとの状態を持たない（規約の `sdk-transport-07`） |
| 使い方のページ | 常駐サーバーの起動・停止・ポートの確認と上書きの手順を、使い方のページに書く |

<!-- /table -->

`決定`: 常駐サーバーの起動と管理の仕方（インターフェース定義設計で決めた）

| 案 | 内容 | メリット | デメリット |
| --- | --- | --- | --- |
| A | systemd --user のユニットを主にし、SessionStart のフックと起動スクリプトは落ちていたときに起動する補助にする。状態の確認・停止・再起動は、サーバーが出す管理の MCP ツールで行う | 規約の `sdk-transport-06` どおり。端末のログインで立ち、落ちても systemd が立て直す | ユニットの登録が端末ごとに要る（setup の手順か反映作業）。外から見る設定の環境変数をユニットへ渡す仕組みが要る |
| B | SessionStart のフックと起動スクリプトが、落ちていればバックグラウンドで起動する（dev-docs と同じ）。systemd は使わない | 端末ごとの登録が要らない。外から見る設定は起動したシェルの環境変数をそのまま受け継ぐ | 規約の「起動と管理は systemd --user を主にする」から外れる |

決定: B

動作環境（`docs/リファレンス/動作環境.md`）の macOS に systemd が無く、A では macOS の端末で主の手段が使えない。
B は dev-docs が同じ形で動いている。
状態の確認と停止は、常駐サーバーが出す管理のツール `server_status`・`server_stop` で行う（規約の管理の MCP ツールに合わせる）。
規約の「起動と管理は systemd --user を主にする」から外れる点は、インターフェース定義『MCP サーバーの起動』の補足に書いた。
