# 要件

## 要望

プラグインの版（`plugins/mindstella/version.ini` の 1 行目）を、リポジトリの直下の `version.ini` の版 `v0.9.0` に揃える。

- `tests/unit/scripts/test_migration_coverage.py::test_plugin_version_not_behind_release_version` が pass する
- 単体テストの全件が、この直しで新しく fail しない（`v0.9.0` の手順は `migrations/` に足さない。v0.9.0 のスプリントはワークスペースの形を変えていない）

リリースで直下の `version.ini` を上げるときに、プラグインの版も同じ版へ揃って上がるようにする。
次のリリース v0.9.1 で直下の `version.ini` が `v0.9.1` になると、プラグインの版が `v0.9.0` のままでは同じテストがまた fail する。

`未確定`: リリースでプラグインの版を揃える手立て（決める段: インターフェース定義設計）

| 案 | 内容 | メリット | デメリット |
| --- | --- | --- | --- |
| A | tester の『リリースマージ』の `version.ini` の更新で揃えるファイルをプロジェクトが指定できるよう、AI Monitor へルール改修を起票し、それまでの間は連絡ボードの tester の節へ、解消する Issue の番号つきで暫定の行を置く | v0.9.1 のリリースから効く。手順の側で直るので、他の版のファイルを持つプロジェクトにも効く | AI Monitor 側の対応を待つ間、暫定の行が残る |
| B | プロジェクトの直下に `agent_context.yaml` を置き、`phase_extensions` で tester にプラグインの版を揃えるフェーズを足す | このリポジトリの中で閉じる | 拡張の行は共通の索引の後ろへ足すだけで、『リリースマージ』の `version.ini` の更新と master へのマージの間に差し込めない |
| C | ルール改修の起票だけを行う | 暫定の行を持たない | AI Monitor 側が直るまでのリリースで同じずれが起きうる |

推奨: A

tester が実際に読む『リリースマージ』は「言語側のバージョンファイル（`pyproject.toml` の `version` 等）があれば同じ値へ揃える」とだけ書き、プラグインの版をそれと読めなかったことが今回のずれの元で、手順の側を直すのが確実なため。
v0.9.1 のリリースまでに効かせるには暫定の行が要る。
