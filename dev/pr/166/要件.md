# 要件

## 要望

ワークスペースにメンバーと役割を持たせ、メンバーを登録したワークスペースではパスワードでログインした人だけがプレビューを使えるようにする。
メンバーを登録しないワークスペースは、今と同じくログインなしで開けた人が全ての操作をできる。

| 対象 | 要件 |
| --- | --- |
| メンバー | `config.yaml` の `members` に、ID・表示名・役割・種類（人 / AI）を持つ。AI の表示名は「AI」で、製品名を出さない |
| 役割 | オーナー・管理者・メンバーの 3 つ。メンバーは見る・回答とコメントの送信・自分の表示の設定ができる。管理者はそれに加えて `config.yaml` の変更（見た目の既定・メンバーの追加・役割の変更）ができる。オーナーはそれに加えて管理者の任命と解任ができる |
| オーナー | メンバーを登録したら最初の 1 人が必ずオーナーになる。オーナーは消せず、降格できない。メンバーが未登録ならオーナーはいない |
| 権限の確かめ | 役割で許さない操作は、画面で出さないだけでなくサーバーが断る（403） |
| ログイン | メンバーを登録したワークスペースでは、ログインしていない要求に画面・記録を返さず、書き込みも受けない。ログインの画面だけを返す |
| 公開範囲 | 既定では `127.0.0.1` だけで待ち受ける。ほかのマシンへ公開するかを `config.yaml` で決める。公開できるのはオーナーがいるときだけで、オーナーがいないのに公開する設定なら、起動時と設定の再読み込みのときにエラーにし、足りないもの（オーナー）を出す。ログインなしでほかのマシンへ公開する手段は設けない |
| パスワードのハッシュ | Argon2id（使えなければ bcrypt）をライブラリで作る。ハッシュはワークスペースの外の `~/.config/mindstella/users.yaml`（本人だけが読み書きできる権限 `0600`）に置き、`config.yaml` には書かない |
| 経路 | HTTPS か、Tailscale・社内 LAN のように守られた経路でだけ使う前提を、公開ドキュメントに書く |
| 失敗が続いたとき | ログインの失敗が続いたら、回数の上限を超えた時点で一時的にロックし、ロックの間はパスワードが合っていても断る |
| Cookie と CSRF | ログインの Cookie は HttpOnly・SameSite を付ける。書き込む操作は CSRF の対策（今の `Origin` の確かめに加えたトークン）を通らなければ断る |
| パスワードを忘れたとき | 管理者が仮のパスワードを発行し、本人は次のログインで新しいパスワードに変えるまでほかの操作ができない。オーナーが忘れたときは、サーバーのマシンで再設定のコマンドを打って変える |

`未確定`: 許可するホスト名（[#138](https://github.com/shuhei1101/mindstella/issues/138) の `MINDSTELLA_ALLOWED_HOSTS`）で外の入口の内側から開く使い方を、ログインとどう組み合わせるか（決める段: 承認確認でユーザーへ確かめる。どちらの案でも #25 か #138 で決めた使い方が変わり、規約『ユーザー確認が必須な事項』の「要件を変える」に当たる。A に決まったら `公開範囲` の行の「ほかのマシンへ公開する」を「待ち受けを `127.0.0.1` の外へ広げる」と書き直す）

| 案 | 内容 | メリット | デメリット |
| --- | --- | --- | --- |
| A | 待ち受けは `127.0.0.1` のまま外の入口が認証を持つ使い方として残し、メンバーを登録していればその内側でもログインを求める。「公開」は待ち受けを `127.0.0.1` の外へ広げることだけを指す | #138 の使い方（自分の端末を外の入口の認証の内側で見る）を壊さない | 外の入口の認証が無い設定でも、メンバー未登録ならログインなしで外から開ける |
| B | 許可するホスト名もオーナーがいるときだけ効かせ、オーナーがいなければ起動時にエラーにする | ログインなしで外から開ける経路が無くなる | #138 の使い方にメンバーの登録とログインが要るようになる |

推奨: A

非機能要件『待ち受けの範囲』が外から開く画面の認証を外の入口に任せると決めており、#138 はその前提で入っている。
#25 の「ほかのマシンへ公開する」は待ち受けのアドレスの設定を指しており、外の入口の内側の使い方まで変えると #138 の利用者の手順が壊れる。

`未確定`: 管理者がメンバーの追加・役割の変更・仮のパスワードの発行を行う場所（決める段: 画面一覧・画面遷移）

| 案 | 内容 | メリット | デメリット |
| --- | --- | --- | --- |
| A | プレビューにメンバーの管理の画面を足し、そこから行う | サーバーが役割を確かめてから書くため、役割の制限が効く | 画面と書き込みの口が増える |
| B | `config.yaml` を手で直して設定の再読み込みで反映し、仮のパスワードだけコマンドで発行する | 画面を足さずに済む | ファイルを直せる人は役割に関係なく何でも変えられ、役割の制限が画面の既定の書き換えにしか効かない |

推奨: A

要望の役割の表は管理者だけが `config.yaml` の変更をできるとしており、サーバーが役割を確かめる口を通さないと制限にならない。

## 変更箇所の由来

| 対象箇所 | commit | 目的 | 変更回数 | 影響 |
| --- | --- | --- | --- | --- |
| `serve.py` の `LISTEN_HOST`（`127.0.0.1`）と非機能要件『待ち受けの範囲』 | [cf56d108](https://github.com/shuhei1101/mindstella/commit/cf56d108df07906321afe1dc790c1968f977d52b)（`サーバーと MCP を前提にした作りへ移し、tmux の起動コマンドで立ち上げたときだけ MCP を立てる (#71)`） | #67 の要件で、配信は記録を読ませ送信でワークスペースへ書くため、端末の外からつながせないと決めた | 1 回 | 公開を「オーナーがいてログインを求めるときだけ」に限れば、記録を読ませ書かせる相手をログインしたメンバーに絞れるため、この目的を壊さない |
| `serve.py` の `check_host`・`check_origin` の許可するホスト名 | [2f979548](https://github.com/shuhei1101/mindstella/commit/2f97954837f1bc3ca7327ed0daf5dcb8e76ec65e)（`トンネル・リバースプロキシの内側で使えるよう、ポートの固定・許可するホスト・起動と終了のフックを設定で足す (#155)`） | 待ち受けは `127.0.0.1` のまま、外の入口の内側から 1 人が自分の端末のサーバーを見るため。外から開く画面の認証は外の入口に任せる | 1 回 | `## 要望` の未確定の案 B はこの使い方にログインを要るようにし、案 A は壊さない |

## スコープ外

| 項目 | 理由 | 対応予定 |
| --- | --- | --- |
| 送信・コメントに送った人のメンバーを記録し、送り元へ返す | 共有サーバーでの送り元の見分けは #14 が持つ | #14 |
| タスクの担当・レビュアーにメンバーを使う | #26 が持つ | #26 |
| 外部の ID 基盤（OAuth・SSO）でのログイン | 要望は自前のパスワードのログインに決めている | 予定なし |
| サーバーが自分で HTTPS を終端する（証明書の設定） | 要望は HTTPS か守られた経路で使う前提にとどめ、HTTPS はリバースプロキシなどの外の入口が持つ | 予定なし |
| 前回開いた日時をメンバーごとに持つ | 前回開いた日時はワークスペースに 1 つで、メンバーを登録すると誰かが開くたびにほかの人の「前回開いてから」の始まりが動く。この PR のメンバーを前提にした後続 | 起票予定 |
| AI のメンバーのログイン | AI は MCP のツールで書き、プレビューを開かない | 予定なし |
